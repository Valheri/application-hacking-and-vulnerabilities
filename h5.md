## lab1

Makefile ei tässä onnistunut debug-symboleita lisäämään joten suoritetaan se itse gcc komennolla (käyttäen lippua **-g** että saadaan debug symbolit) ja sitten suoritetaan ohjelma gdb:llä.
```
gcc -g gdb_example1.c -o gdb_example1
gdb gdb_example1
```

Suoritetaan ohjelma **run** komennolla ja huomataan kuinka ohjelma kaatuu sekä antaa tulosteessa errorin:

```
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
0x0000555555555163 in print_scrambled (message=0x0) at gdb_example1.c:7
7	    printf("%c", (*message)+i);
```
Tästä saamme tietää että message rivillä 7 on null(=0x0)

Korjaukseksi null tarkistus ennen riviä 7 (oikeaoppisesti myös error viesti olisi hyvä)
```
if (message == NULL) {
    return;
  }
```

## lab2
Tämän harjoituksen voi selvittää jo aiemmin tunneilla oppitulla strings komennolla
```
strings passtr
```
jonka tulosteesta voi aika selvästi löytää salasanan **sala-hakkeri-321**
```
What's the password?
%19s
sala-hakkeri-321
```
Uuden oppimisen vuoksi lähdin tutustumaan hieman gdb **disassemble** hyödyntämiseen. Opin että sieltä voi paikantaa merkkijono vertailun **strcmp** (string compare) funktio kutsuna (call), tästä sain hyvän breakpointin. Tein myös oletuksen että edeltävän move komennon (mov    %rdx,%rsi ja mov    %rax,%rdi) on ne muistit mität käytettiin(salasana sekä syöte.)
```
(gdb) dissasemble main
...
0x0000555555555196 <+61>:	mov    %rdx,%rsi
0x0000555555555199 <+64>:	mov    %rax,%rdi
0x000055555555519c <+67>:	call   0x555555555040 <strcmp@plt>
...
(gdb) b *main+67

```
sitten suorituksesta voi poimia muistiosoitteissa olevan salasanan ja syötteen **x/s** komennoin(tosin salasana nyt näkyy debugs-symbolien avulla jo tulosteessa)
```
(gdb) run
What's the password?
asd

Breakpoint 3, 0x000055555555519c in main () at passtr.c:12
12		if (0 == strcmp(password, "sala-hakkeri-321")) {
(gdb) x/s $rdi
0x7fffffffde50:	"asd"
(gdb) x/s $rsi
0x555555556022:	"sala-hakkeri-321"
(gdb) x/s $rdx
0x555555556022:	"sala-hakkeri-321"
```
Opin x/s komennon hyödyn ja taas lisää disassemblen lukemista.

## lab4 (lisätehtävä)


#### 1. Epäonnistumiset ja muistiosoiteongelmat (PIE)

Harjoituksen alussa yritin asettaa katkopisteitä suoraan offset-osoitteisiin `disassemble main` -tulosteen perusteella. Suoritus kuitenkin epäonnistui virheilmoitukseen:

```text
(gdb) b *main+16
Breakpoint 1 at 0x1438
(gdb) run
Warning:
Cannot insert breakpoint 1.
Cannot access memory at address 0x1438

```

Myös pelkkä `b main` epäonnistui samasta syystä ennen ohjelman käynnistämistä. Syyksi paljastui binäärissä käytössä oleva **PIE-suojaus** (*Position Independent Executable*). Binääri ladataan muistiin dynaamisesti vasta suorituksen alkaessa, joten staattiset offset-osoitteet eivät ole voimassa ennen kuin prosessi on käynnissä ja muistiavaruus kartoitettu.

#### 2. Analyysi ja havainnot (Main & checkPassword)

Ratkaisin muistiongelman käynnistämällä ohjelman suoraan GDB:n `start`-komennolla, joka latasi prosessin muistiin ja pysäytti suorituksen automaattisesti `main`-funktion alkuun.

Tutkimalla `main`-funktion disassemblyä kävi ilmi, että koodi ei suorita vertailua suoraan `mainissa`. Sen sijaan `main` kutsuu erillistä tarkistusfunktiota:

```
0x...5492 <+106>: call <_Z13checkPassword...>

```

Siirryin tutkimaan kyseistä funktiota komennolla `disassemble checkPassword`. Asettamalla katkopisteitä kutsuihin huomasin, että ohjelma poistui kesken kaiken eikä edennyt funktion loppuun asti. Assemblystä paljastui syötepituuden tarkistus, joka keskeytti suorituksen heti, jos syöte oli väärän pituinen. Riviltä `<+62>` löytyi `$0xfffffff9` (-7).

Ensimmäisellä muistitarkastelulla osoitteesta `0x555555556005` löytyi vain osittainen merkkijono `"dec"`. Tästä selvisi, että koodi rakentaa salasanaa dynamiikka-silmukassa paloista.

#### 3. Salasanan kaivaminen muistista ja ratkaisu

Ajoin ohjelman uudelleen antamalla syötteeksi 7 merkkiä pitkän valesalasanan (`1234567`), jolloin suoritus läpäisi pituustarkistuksen ja eteneminen jatkui silmukan yli.

Silmukan jälkeen (kohta `<+243>`) salasana oli jo rakennettu muistiin pinoalueelle. Disassemblystä havaittiin, että string-olion rakenne sijaitsi pinossa 96 tavua (`0x60` heksana) pino-osoittimen kantarekisterin (`%rbp`) alapuolella (`-0x60(%rbp)`).

Loin AI:n avulla muistiosoitepyynnön GDB:n komentosyntaksilla ja luin pinossa olevan osoittimen osoittaman raakadatan:

```text
(gdb) b *checkPassword+243
(gdb) continue
(gdb) x/s *(void**)( $rbp - 0x60 )
$1 = "dekcarc"

```

Tuloksena muistista paljastui merkkijono `"dekcarc"`.

Kääntämällä merkkijonon takaperin saatiin lopullinen oikea salasana: **`cracked`**.
